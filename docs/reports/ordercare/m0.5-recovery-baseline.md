# OrderCare M0.5：FlowOrder 恢复域基线

> 日期：2026-07-17
> 状态：首个纵向切片已通过，M0.5 整体仍在进行中
> 范围：超时状态消息死信恢复，不代表 RabbitMQ 跨服务 E2E 已完成

## 1. 本轮目标

在接入 Agent 前先验证 FlowOrder 恢复域，避免用可靠的 Agent 编排包装不可靠的底层恢复接口。本轮只处理三个高优先级问题：

1. 区分恢复命令提交状态与业务收敛结果。
2. 固化死信业务键、收敛规则和消费幂等测试。
3. 用真实 Spring 事务和 MySQL 验证超时状态死信的恢复纵向切片。

## 2. 状态语义修订

恢复动作数据库状态码 20 保持兼容，但对外语义由 `SUCCEEDED` 改为 `SUBMITTED`：

```text
PREVIEWED -> EXECUTING -> SUBMITTED / FAILED
```

重复提交同一 `actionRequestId` 返回 `IDEMPOTENT_SUBMITTED`。`SUBMITTED` 只证明恢复命令已经可靠提交；订单、库存、扣减和死信是否收敛必须单独判断。

## 3. 自动化证据

### 3.1 单元测试

```powershell
mvn -pl floworder-server/floworder-resource-service -am "-Dtest=MqDeadLetterServiceTest,RecoveryServiceImplTest" "-Dsurefire.failIfNoSpecifiedTests=false" test
```

结果：

```text
Tests run: 9, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

覆盖内容：

- `ORDER_CONFIRMED -> SOLD`、`ORDER_CANCELLED/ORDER_TIMEOUT -> RELEASED`。
- 未知状态事件不得误判为收敛。
- 创建、结果、状态三类死信使用 `deductNo` 作为 `bizKey`。
- 创建消息无法解析时从 resource-service Outbox 恢复业务键。
- 同一恢复动作重复 execute 返回 `IDEMPOTENT_SUBMITTED`，领域恢复只调用一次。

### 3.2 MySQL 集成测试

```powershell
mvn -pl floworder-server/floworder-resource-service -am "-Dtest=DeadLetterRecoveryBaselineIntegrationTest" "-Dsurefire.failIfNoSpecifiedTests=false" test
```

结果：

```text
Tests run: 4, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

测试类：

```text
floworder-server/floworder-resource-service/src/test/java/
com/javaup/resource/mq/DeadLetterRecoveryBaselineIntegrationTest.java
```

| 场景 | 自动化断言 | 结果 |
|---|---|---|
| 超时状态死信重放 | `PENDING -> REPLAYING -> 消费 -> RESOLVED` | 通过 |
| 重复消费同一 messageId | consume log 仅 1 条，库存只释放一次 | 通过 |
| 两线程并发重放 | 只有一个 CAS 抢占成功，远程提交只调用一次 | 通过 |
| stale REPLAYING 且业务已收敛 | 死信转 `RESOLVED` | 通过 |
| stale REPLAYING 且业务未收敛 | 死信 CAS 回 `PENDING`，库存保持未释放 | 通过 |
| 业务最终状态 | 预约 TIMEOUT、扣减 RELEASED、锁定库存归还、额度释放、库存恒等式成立 | 通过 |

集成测试通过 Mockito 隔离 Redis，并关闭 RabbitMQ Listener 自动启动；数据库读写、事务、MyBatis-Plus Mapper 和 CAS 使用本机真实 MySQL。

## 4. 当前边界

本报告不能证明以下能力已经完成：

- order-service 收到重放命令后经 RabbitMQ 真实重新投递状态消息；当前 HTTP 重放边界使用 mock。
- 创建消息和订单结果消息的真实重放 E2E。
- 两个定时扫描器同时处理同一 stale REPLAYING 记录的并发证据。
- 可供人工演示的一键异常注入和清理脚本。

因此 M0.5 仍为进行中，尚不能开始 OrderCare 业务工具编码。
