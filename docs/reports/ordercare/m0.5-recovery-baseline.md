# OrderCare M0.5：FlowOrder 恢复域基线

> 日期：2026-07-17
> 状态：`PASSED`
> 主证据：真实 MySQL、真实 RabbitMQ、order-service 与 resource-service 跨服务重放

## 1. 放行结论

在接入 Agent 业务工具前，FlowOrder 已经证明以下恢复基础成立：

1. 恢复命令提交状态与业务收敛结果相互独立。
2. 创建、结果、状态三类死信均以 `deductNo` 作为业务关联键。
3. 同一 `messageId + consumerGroup` 重复消费不会重复释放库存。
4. stale `REPLAYING` 能根据业务事实转为 `RESOLVED` 或 CAS 回 `PENDING`。
5. 两个扫描器处理同一记录时只有一个数据库状态迁移成功。
6. 超时状态死信能够经过真实 HTTP、Outbox、RabbitMQ 和消费者链路恢复。
7. 异常数据可以通过固定脚本注入、查询和清理。

因此 M0.5 门禁通过，可以开始 M1 的案例聚合接口和 Agent 只读诊断。

## 2. 状态语义

Recovery Action 数据库状态码 20 保持兼容，但对外语义由 `SUCCEEDED` 修正为 `SUBMITTED`：

```text
PREVIEWED -> EXECUTING -> SUBMITTED / FAILED
```

重复提交同一 `actionRequestId` 返回 `IDEMPOTENT_SUBMITTED`。`SUBMITTED` 只证明恢复命令已经可靠提交；订单、库存、扣减和死信是否收敛由独立的业务结果判断。

stale 死信扫描返回实际完成状态迁移的记录数。该数字来源于数据库 CAS 结果，所以两个实例不能同时报告拥有同一条恢复记录。

## 4. 真实 RabbitMQ 跨服务 E2E

### 4.1 链路

```text
固定 SQL 注入超时状态死信
-> resource-service /internal/mq/dead-letter/{id}/replay
-> Feign OrderMqAdminClient
-> order-service 将原 Outbox SENT 重置为 RETRY
-> order-service Outbox Publisher
-> RabbitMQ floworder.order.state.exchange
-> resource-service OrderStateConsumer
-> messageId + order-state-consumer 幂等日志
-> 释放库存和额度
-> 死信 RESOLVED
```

运行条件：MySQL `3306`、Redis `6379`、RabbitMQ `5672`、Nacos `8848`，以及 order-service `8082`、resource-service `8081`。

执行命令：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/ordercare/m0.5-recovery-baseline.ps1 `
  -Action Scenario `
  -DbPassword $env:FLOWORDER_MYSQL_PASSWORD
```

### 4.2 E2E 发现并修复的运行缺口

- 两个服务原来只声明了 Spring Boot 插件，没有绑定 `repackage`，`mvn package` 产物不能通过 `java -jar` 启动；现已生成包含 `BOOT-INF` 的可执行 JAR。
- 恢复管理 Controller 依赖隐式 Java 参数名，但构建未启用 `-parameters`，运行时无法绑定 PathVariable；现已显式声明所有相关参数名。

## 5. 可复现脚本

入口：`scripts/ordercare/m0.5-recovery-baseline.ps1`

| Action | 用途 |
|---|---|
| `Verify` | 运行 15 条恢复基线测试 |
| `Inject` | 清理旧夹具并注入固定异常链路 |
| `Replay` | 调用死信重放接口 |
| `Inspect` | 查询订单、扣减、库存、死信和消费日志 |
| `Cleanup` | 删除固定测试数据 |
| `Scenario` | Inject、Replay、等待消费并输出最终证据 |

固定夹具只使用 `ORDERCARE-M05-*` 业务键和 `900000000000050x` ID，并显式创建订单服务已 `TIMEOUT` 的 `fo_reservation_order` 事实；清理脚本不按宽泛条件删除业务数据。

## 6. 已知边界

- 真实 broker E2E 固定为首个主案例“超时状态消息死信恢复”；创建消息和结果消息目前由单元测试及真实 MySQL Listener 集成测试覆盖，没有宣称三类消息都完成 broker E2E。
- 本地管理接口仅在 `floworder.admin.enabled=true` 时出现，尚未加入服务认证；该项属于后续 M4 安全边界。
- M0.5 只证明 FlowOrder 恢复域可被 Agent 编排，不代表 Proposal、HITL、UNKNOWN 对账和 Agent 重启恢复已经完成。
